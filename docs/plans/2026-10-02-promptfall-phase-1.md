# Promptfall phase 1 implementation plan

**Goal:** A solo-playable Promptfall: the band and dialog inside Claude Code, driven by a deterministic sim, persisted locally, already speaking the authenticated batch protocol to an in-process fake server.
**Architecture:** A pnpm monorepo with two pure packages, `@promptfall/sim` (deterministic game rules and content) and `@promptfall/protocol` (Zod schemas, the `ServerClient` interface, an in-process fake server and the contract suite), bundled by tsup into the plugin folder `plugins/promptfall`, whose hooks run the sim locally, buffer events into batches, reconcile hashes with the fake, and draw the band above the prompt and a dialog pane.
**Spec:** `docs/spec/promptfall.md`
**Execution model:** opus
**Review wave:** done on 2026-10-02 (reviewer on opus, reviewer on fable, codex-review on gpt-6-astra); this is the fixed plan. No second wave.

## Global constraints

- Sim is integer only: no floating point values in state, fixed-point percentages in basis points (10000 = 100%), no `Date`, no `Math.random`, no `Math` call other than `Math.imul`, `Math.floor`, `Math.max`, `Math.min`, `Math.abs`. A grep for `Math.random|\bDate\b|\d\.\d` under `packages/sim/src` (tests excluded) must be empty.
- The sim is purely event driven. No timestamps inside `@promptfall/sim`. Cadence (2 s during a turn, 5 s idle) is the plugin's scheduling.
- Rarity tiers in this order everywhere: `common`, `uncommon`, `rare`, `epic`, `legendary`. Affix and trait counts by rarity: 0, 1, 2, 3, 4. Level caps: 20, 30, 40, 45, 50. Item base stat multipliers: 10000, 11000, 12000, 13500, 15000 basis points.
- Classes: `knight`, `black_mage`, `white_mage`, `archer`. Slots: `weapon`, `armour`, `accessory`. Stats: `hp`, `atk`, `def`, `spd`.
- 12 zones, 10 waves plus a zone boss each, 1 to 3 enemies per wave, at most 3 enemies fighting at once and at most 10 queued.
- Starting state: one Common hero per class, party Knight, Black Mage, White Mage, 0 gold, zone 1 wave 1, inventory cap 30, roster cap 24.
- Inventory holds every item the account owns, equipped or not; equipped items occupy slots.
- Rest heals 30% and revives at 30%; wave clear heals 15% and revives at 15%; wipe retreats one zone, never below zone 1, full heal.
- Turn boss spawns when a turn ends after 10 or more tool calls, counted by the sim itself.
- Inventory full: the drop is auto-vendored and logged. Loot log keeps the last 50 entries.
- Batches flush every 15 seconds; a batch carries `batchId`, `accountId`, `seq`, `clientVersion`, `simVersion`, `baseHash`, `resultHash`, `events`, and is submitted with the device token. Server replays and wins on mismatch.
- The plugin calls only `$.ui`, `$.state`, `$.store`, `$.clock`, `$.command`. `claude plugin validate` output must list no `fs`, `process`, `model`, `prompt`, `audio`, `http` or `session` calls. (`$.http` joins in phase 2.)
- The plugin ticks only in a session that is interactive on the `terminal` surface at `session.start`, or that a `desktop` client attaches to.
- Band: 4 rows at rest, 1 row collapsed, collapsed automatically under 100 `bodyColumns` or under 4 `maxRows`, hidden while `hasSurvey`, off per session on command. Hotkeys are letters.
- Bundles under `plugins/promptfall/hooks/vendor/` and `plugins/promptfall/hooks/version.ts` are generated by `pnpm vendor` and committed; CI fails if they are stale.
- CI covers lint, typecheck, package tests and vendor freshness. `claude plugin validate`, `claude plugin test` and `tsc -p plugins/promptfall` run locally as acceptance checks; wiring them into CI is a phase 5 concern.
- Language, commits and docs in English. Commits end with the attribution lines given in the session.
- Branch flow: the repository is initialised with `ai-staging` as its default branch (no `main` exists until Kevin creates it, so nothing in this plan lands on `main`); work happens on `feat/phase-1`; at the end a PR from `feat/phase-1` into `ai-staging`.

`step` never throws on a well-typed event: an invalid command (unknown id, wrong class, not enough gold, hero in party dismissed, item equipped elsewhere) returns the same state object and one `rejected` effect with a `reason` from the list in Task 5. `step` never mutates its input. Returned state is a fresh object graph where it changed; unchanged subtrees may be shared.

### PRNG (verbatim, `packages/sim/src/rng.ts`)

mulberry32. Roll with modulo; the bias is irrelevant and determinism is the point.

```ts
export function nextU32(s: number): { s: number; u: number } {
  s = (s + 0x6d2b79f5) >>> 0
  let t = s
  t = Math.imul(t ^ (t >>> 15), t | 1)
  t ^= t + Math.imul(t ^ (t >>> 7), t | 61)
  return { s, u: (t ^ (t >>> 14)) >>> 0 }
}
export function roll(state: GameState, n: number): { state: GameState; value: number }  // value in [0, n), n >= 1
export function rollBp(state: GameState): { state: GameState; value: number }           // [0, 10000)
export function pickWeighted<K extends string>(state: GameState, weights: Record<K, number>): { state: GameState; value: K }
```

`pickWeighted` iterates the keys sorted by UTF-16 code unit order, never by object insertion order, so two engines agree.

### Hash (verbatim rules, `packages/sim/src/hash.ts`)

`canonicalJson(value)`: objects with keys sorted by UTF-16 code unit order, arrays in order, no whitespace, integers as `JSON.stringify` prints them, `null` kept, `undefined` fields dropped. `hashState(state) = fnv1a32(json, 0x811c9dc5) ++ fnv1a32(json, 0x050c5d1f)`, each as 8 lowercase hex chars, where

```ts
function fnv1a32(text: string, offset: number): number {
  let h = offset >>> 0
  for (let i = 0; i < text.length; i++) {
    h ^= text.charCodeAt(i)
    h = Math.imul(h, 0x01000193) >>> 0
  }
  return h
}
```

### Ids (`packages/sim/src/ids.ts`)

`nextId(state, prefix: 'h' | 'i' | 'e')` returns `{ state, id }` with `id = prefix + state.counter.toString(36)` and `counter + 1`. Unique within a state lineage; a server prefixes the account id when it needs global ids.

### `@promptfall/protocol` public API (`packages/protocol/src/index.ts`)

```ts
export const PROTOCOL_VERSION = 1 as const
export const HEX16: z.ZodString                      // /^[0-9a-f]{16}$/
export const TimedEventSchema: z.ZodType<TimedEvent>  // Event & { at: number }, at = client ms epoch
export type TimedEvent = Event & { at: number }
export const BatchSchema: z.ZodType<Batch>
export type Batch = {
  batchId: string        // 16 to 64 chars, client generated (crypto.randomUUID), unique per account
  accountId: string
  seq: number            // 0-based, +1 per committed batch
  clientVersion: string  // semver string of the plugin
  simVersion: number
  baseHash: string       // hash before the batch's events
  resultHash: string     // hash after
  events: TimedEvent[]   // 1 to 2000
}
export type Auth = { deviceToken: string }
export type BatchAck =
  | { ok: true; seq: number; hash: string; duplicate: boolean }                       // seq: the next expected
  | { ok: false; reason: 'unauthorized' }
  | { ok: false; reason: 'version_gate'; minClientVersion: string }
  | { ok: false; reason: 'sim_version'; simVersion: number }
  | { ok: false; reason: 'seq_mismatch'; seq: number; state: GameState; hash: string }  // seq: the next expected
  | { ok: false; reason: 'hash_mismatch'; seq: number; state: GameState; hash: string; revokedItemIds: string[] }
  | { ok: false; reason: 'rate_capped'; seq: number; state: GameState; hash: string; kind: EventKind }
export type ServerConfig = { minClientVersion: string; simVersion: number; flags: Record<string, boolean> }
export type Account = {
  accountId: string; seed: number; createdAt: number; displayName: string | null
  linked: null | { provider: 'github'; login: string }
}
export type Bootstrap = { deviceToken: string; account: Account; config: ServerConfig; state: GameState; seq: number; hash: string }
export interface ServerClient {
  bootstrap(input: { clientVersion: string; deviceToken: string | null }): Promise<Bootstrap>
  submit(batch: Batch, auth: Auth): Promise<BatchAck>
}
export interface KeyValue {
  get(key: string): Promise<unknown>
  set(key: string, value: unknown): Promise<void>
  delete(key: string): Promise<void>
}
export class MemoryKeyValue implements KeyValue
export const BUDGETS: Record<'tick' | 'tool_call' | 'rest' | 'turn_end', { refillMs: number; capacity: number }>
// tick { 2000, 70 }, tool_call { 1000, 140 }, rest { 5000, 30 }, turn_end { 5000, 30 }
export type LocalServerOptions = { kv: KeyValue; now: () => Promise<number>; minClientVersion: string; seedSource: () => number; tokenSource: () => string }
export class LocalServer implements ServerClient { constructor(options: LocalServerOptions) }
export function compareSemver(a: string, b: string): -1 | 0 | 1
```

The contract suite is not part of the root export, so the plugin bundle never carries vitest. It lives at the subpath `@promptfall/protocol/contract` (`packages/protocol/src/contract/index.ts`, declared under `exports` in the package's `package.json`):

```ts
export type ContractClock = { now: () => Promise<number>; advance: (ms: number) => void }
export function runServerContract(name: string, make: (clock: ContractClock) => Promise<ServerClient>): void
```

Server rules every `ServerClient` must satisfy, applied in this order (the contract suite asserts each):

0. Schema: a `submit` whose batch fails `BatchSchema` (empty `events`, over 2000, malformed hash, short `batchId`) is rejected before anything else; the fake throws a `ZodError`, the HTTP servers later answer 400.
1. `bootstrap` with `deviceToken: null` mints an account (`accountId`, `seed` from `seedSource`, token from `tokenSource`), stores `createInitialState(seed)` at `seq 0`, a full set of budgets (each at its capacity) and `T0 = now`, and returns it with `hash === hashState(state)`.
2. `bootstrap` with a known token returns the same account, the current state, the next expected `seq` and its hash. `bootstrap` with an unknown token mints a new account.
3. `submit` whose `auth.deviceToken` is unknown, or maps to an account other than `batch.accountId`, returns `unauthorized`.
4. `submit` with `clientVersion` below `minClientVersion` (`compareSemver`) returns `version_gate`. `simVersion !== SIM_VERSION` returns `sim_version`.
5. `submit` with a `batchId` already committed for that account returns `{ ok: true, duplicate: true }` with the hash and next seq recorded then, and changes nothing.
6. `submit` with `seq !== expectedSeq` returns `seq_mismatch` with the authoritative state, hash and expected seq.
7. `submit` with `baseHash !== hashState(current)` returns `hash_mismatch` with the authoritative state, `revokedItemIds: []`, and the expected seq.
8. Budgets: with `T = now` and `T0` the server time of the last commit, every bucket refills by `floor((T - T0) / refillMs)` tokens, clamped to `capacity`. For each kind in `BUDGETS`, the batch's count of that kind must not exceed the bucket; otherwise `rate_capped` naming the first `kind` that failed, nothing applied, no tokens consumed, `T0` unchanged.
9. Commit: the server replays the events with `replay`. Whether or not `hashState(result)` equals `resultHash`, it stores the result, records the `batchId` with the result hash, increments `seq`, consumes the tokens, and sets `T0 = T`, in one write path so no partial commit exists. On match it returns `{ ok: true, duplicate: false, seq: next, hash }`. On mismatch it returns `hash_mismatch` with the server state, the next seq, and `revokedItemIds`: ids present in `batch`'s claimed result but absent in the server result, which the fake computes by replaying the client's claim only when it has it (phase 1: the client's claim is not sent, so the list is empty; the field exists so phase 5 can fill it).

- `heroStats`: `base + growth * (level - 1)`, plus the sum of equipped item stats (items looked up by id in `inventory`) where each item's base stats are multiplied by its rarity `statMultBp / 10000` and its affixes add `value` to their stat, plus traits applying `valueBp` percentage bonuses to their stat, all in integer arithmetic with floor at each multiplication. - `tick`, in this order: (1) if an encounter is open, move queued enemies into `enemies` while fewer than 3 are living; (2) if any enemy is living, resolve one round and stop; (3) otherwise, if `pendingTurnBoss`, spawn the zone's `turnBoss` as a single enemy of kind `turn_boss`, clear the flag, emit `boss_spawned`; else if `wave === 11`, spawn the zone's `boss` as a single enemy of kind `zone_boss`, emit `boss_spawned`; else open the wave's encounter if none is open (`waveSize = 1 + roll(3)`) and spawn one wave enemy, `spawnedInWave + 1`. - A round: actors are living heroes then living enemies, sorted by `spd` descending, ties keeping that order. Each acts once. Damage from attacker with `atk` against defender with `def` is `max(1, floor(atk * v / 10000) - floor(def / 2))` with `v = 9000 + roll(2001)`. Knight attacks the first living enemy. While any Knight lives, each enemy targets a uniformly chosen living Knight with probability 6000 bp (`rollBp() < 6000`), else a uniformly random living hero. Black Mage hits every living enemy with damage computed from `floor(atk * 6000 / 10000)`. White Mage heals the lowest-hp living hero by `floor(atk * 8000 / 10000)` when that hero is under 7000 bp of max hp, else attacks the lowest-hp enemy. Archer attacks the lowest-hp enemy with a 2000 bp chance of double damage. A hero at 0 hp emits `hero_fell` and stops acting. An enemy at 0 hp is removed, grants its `xp` to every living party hero and its gold (`roll` in the inclusive range) to the account with a `gold` effect, counts in `stats.kills` (bosses also in `stats.bosses`), and `rollDrops(state, def)` is called.
- Wave clear: when no living enemy remains, the queue is empty and `spawnedInWave === waveSize`: heal every party hero 1500 bp of max hp and revive the fallen at 1500 bp, emit `wave_cleared`, set `encounter = null`, advance `wave` by one (10 goes to 11, the boss).
- Zone boss killed: `encounter = null`, `zone_cleared`; if `farm` is false and `zone < 12`, `zone + 1`, `wave 1`, `highestZone` updated; if `farm` is true or `zone === 12`, `wave 1` in the same zone. Turn boss killed: `encounter = null` if nothing else lives, no wave change.

**Work:**

Gating in `register`: on `session.start`, when `e.isInteractive && e.surface === 'terminal'`, start the engine; otherwise return `next(e)` and wait. On `session.attach` with `e.surface === 'desktop'`, start the engine if it is not running. Starting means: build `StoreKeyValue`, `LocalServer({ kv, now: () => $.clock.now(), minClientVersion: CLIENT_VERSION, seedSource, tokenSource })` where `seedSource` is `parseInt(crypto.randomUUID().slice(0, 8), 16)` and `tokenSource` is `crypto.randomUUID()`, then `GameEngine` with `newBatchId = () => crypto.randomUUID()` and `publish` writing the atoms; then the lease; then timers.

Hooks, each returning `next(e)` unchanged and each beginning with `const at = await $.clock.now()`: `turn.start` without `agentId` switches the tick interval to 2000 ms; `tool.call` applies `tool_call` (subagent tool calls count: they are Claude's work); `turn.complete` without `agentId` applies `turn_end` and switches the interval to 5000 ms, with `agentId` it is ignored; `prompt.submit` applies `rest` only when `e.origin.kind === 'composer'`. Timers: one `$.clock.every` for ticks, cancelled and recreated when the cadence changes; one of 15000 ms calling `flush`; one of 10000 ms renewing the lease. All hooks and timers apply events only while `mode === 'primary'`.

Lease (`lease.ts`): key `lease` in `StoreKeyValue`, value `{ owner: string; until: number }`, TTL 30000 ms. `acquire(kv, owner, now)`: read; if the key is missing, expired, or owned by `owner`, write `{ owner, until: now + 30000 }`, then read again and succeed only if the owner read back is `owner`. The owner id is `crypto.randomUUID()` generated once and kept in the `leaseOwner` atom so a hot reload (which re-runs `session.start`) reuses it and keeps primacy. Holding the lease is `primary`; failing to acquire is `secondary`: no events, no tick, and every 10 s a view refresh through `client.bootstrap` with the stored token, which is read-only for the fake. A secondary that later acquires the lease becomes primary by calling `start()` again.

Buffering and flushing: the buffer holds `{ events: TimedEvent[]; baseHash: string }`, `baseHash` taken when the first event enters an empty buffer. `flush` is single flight: if one is in progress, return; otherwise swap the buffer for a fresh one and submit the swapped one with `baseHash`, `resultHash = hashState(local state at swap time)`, `seq`, and `auth: { deviceToken }`; events applied during the flight go to the fresh buffer. Ack handling: `ok` sets `seq` to the ack's seq (`duplicate` included); `seq_mismatch` and `rate_capped` adopt the server's state, hash and seq, clear both buffers, and set `notice` for 10 s (`Promptfall resynced` and `Promptfall: progress capped, resynced`); `hash_mismatch` adopts state, hash and seq silently, and toasts `An item was revoked` only when `revokedItemIds` is non-empty; `version_gate` and `sim_version` call `setPaused` with a notice that stays (`Update Promptfall: /plugin update promptfall`); `unauthorized` pauses with `Promptfall: account mismatch, delete the plugin store to reset`. A thrown error from `submit` (the fake throws only on a schema bug) pauses with the error's name. Hot reload note: `session.start` fires again on reload, timers are dropped and recreated, the buffer's unflushed events (at most 15 s) are lost, and the cadence restarts at 5000 ms until the next `turn.start`.

`toGameView`: hero rows for the party in party order; living enemies; zone name from content; last 12 loot entries rendered as `"<glyph> <name> (<rarity>)"` or `"<name> sold for <gold>g"`; inventory and roster views with the derived prices; `tavernPrice` by the Task 5 formula; `nextInventoryCost`/`nextRosterCost` null at max; `firstRun` true when the bootstrap minted the account in this start.
